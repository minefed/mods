# 2026-10-17 서버 틱 부하 개선과 자동 진단

[서버 rx 감소·ticks behind 조사](SERVER_STALL_AUDIT_2026-10-17.md)에서 확인한 경로 중
동작을 유지하면서 줄일 수 있는 반복 계산과 잘못된 입력의 서버 작업을 수정했다.
디스플레이, Oritech, MTR 변경은 각 저장소의 `minefed-1.20.4`에 병합·push했다.
**운영 서버에는 배포하지 않았으며, 이번 장애의 원인 확정이나 운영 TPS 개선율 측정은 아니다.**

기준은 Minecraft 1.20.4 / Fabric Loader 0.18.4 / Java 17이다. 전체 소스 커밋,
JAR 경로·크기·SHA-256·SHA-512와 라이선스는
[이번 변경의 바이너리 기록](../inventory/server-tick-improvements-2026-10-17.json)에 보관한다.
기존 조사 보고서는 수정 전 소스와 당시 증거를 설명하므로 아래 변경 이후 상태와 구분해서 읽는다.

### 디스플레이

가로·세로 각각 1–32블록인 기존 유효 범위를 서버에서도 적용한다. 범위 밖 크기는
서버 작업을 등록하거나 월드 블록을 읽기 전에 거부하므로, 과도한 입력이 큰 영역을
순회하지 않는다. NBT에서 읽은 크기도 같은 범위로 보정한다. 로드되지 않은 대상의
설정 패킷은 청크를 새로 읽어 오지 않고 무시한다. 해당 디스플레이로 돌아온 뒤 설정을
다시 열어 변경할 수 있다.

유효한 확대·축소, URL만 변경, 표시판의 어느 부분을 부수든 연결된 표시판을 제거하는
동작은 유지한다. 실제 블록·블록 엔티티·NBT와 모의 월드를 쓰는 서버 검사 7개가
통과했다. 잘못된 크기·정수 범위 초과, 월드 읽기 이전 거부, 미로딩 대상, 모든 방향의
유효 경계 크기, 확장 공간 충돌, 축소·파괴, URL 보존과 NBT 왕복을 확인했다.
렌더링·브라우저 관련 검사의 범위는 [모드 README](../minefed-display/README.md)에 정리했다.

이는 입력 검증과 불필요한 월드 접근 제거다. **정상 최대 크기인 32×32블록을 실제로
설치·확대할 때의 블록 변경과 이웃 갱신 비용은 남아 있다.** 서버 실행 중 전체 모드팩의
청크 생성·이웃 갱신 비용을 이 단위 검사로 측정한 것은 아니다.

### Oritech

레이저의 한 번의 동기 탐색 안에서 이미 통과 가능하다고 확인한 블록의 중복 조회를
줄였다. 캐시는 호출이 끝나면 버리고, 청크 로드가 필요해 서버의 대기 작업이 실행될
가능성이 있으면 그 전에 비운다. 다음 탐색의 월드 변경과 청크 로드 중 변경을 다시 읽는다.

영역 탐색은 기존처럼 모든 셀을 읽되, 거리 정렬을 안정적인 계수 정렬로 바꾸고 실제로
보관할 목표에만 불변 좌표를 만든다. 같은 거리의 목표 순서, 전체 목표 큐, 최초 광선
충돌과 새 좌표의 첫 조회 순서, 목표를 선택하는 틱은 유지한다. 작업을 다른 틱이나
월드 접근이 안전하지 않은 작업 스레드로 옮기지 않았다.

[탐색 검증](../Oritech/src/laserVerification/README.md)은 수정 전 메서드를 보존한 기준
구현과 실제 Minecraft `BlockPos`·`Vec3d`를 사용한다. 고정 난수 입력과 음수 좌표,
월드 경계, 정확한 복셀 경계, 거리 동률, 빈 영역·막힌 영역, 호출 사이 편집,
청크 로드가 이미 읽은 블록을 바꾸는 경우를 비교한다. 영역의 전체 월드 조회는 계속
필요하며, 실제 청크 조회·생성 비용을 없애거나 기계 작동 빈도를 낮추는 변경은 아니다.

레이저 검사 5,104개 assertion, GUI 검사 96개, 인벤토리 검사 433개가 통과했고,
Java 17 / Fabric 1.20.4 빌드를 마쳤다. 순수 탐색 커널에서 측정한 결과는 다음과 같다.

| 합성 입력과 측정 항목 | 이전 | 변경 후 |
| --- | ---: | ---: |
| 빈 공간의 128블록 축 방향 광선: 블록 상태 조회 | 2,562회 | 129회 |
| 반경 16, 목표가 조밀한 영역: 커널 실행시간 | 9.180ms | 2.788ms |
| 같은 조밀한 영역: 스레드 할당량 | 1,617,520B | 1,618,520B |
| 반경 16, 목표가 드문 영역: 커널 실행시간 | 3.169ms | 1.344ms |
| 같은 드문 영역: 스레드 할당량 | 865,720B | 156,934B |

조밀한 영역의 할당량은 약 0.06% 늘었으며 모든 입력에서 메모리가 감소하는 것은 아니다.
광선의 새 좌표 조회 전에는 비차단 청크 준비 상태 확인도 수행하므로 블록 상태 조회 감소를
모든 월드 접근 비용의 같은 비율 감소로 해석하지 않는다. 위 수치는 합성 탐색 커널의
비교이며 운영 서버 TPS·MSPT 개선율이 아니다.

### MTR

30초마다 만드는 정적 교통 정보에서 변경 불가능한 Core `RailMath` 객체의 곡선 좌표를
재사용한다. 선로 ID가 같아도 형상이 바뀌어 새 객체가 생기면 다시 계산한다. 선로와
노선 구간에 쓰던 서로 다른 부동소수점 식과 좌표 필터를 그대로 유지한다. 완성한 좌표
배열은 전송 중에도 수정하지 않는다.

캐시는 월드별 131,072좌표·4,096배열로 제한하고 사용하지 않은 곡선은 다음 캡처 끝에
제거한다. 한 배열이 한도를 넘으면 정상 계산하되 보관하지 않는다. 전송 중인 스냅샷은
배열을 더 보유할 수 있으므로 이 수치는 JVM 전체 메모리 상한이 아니다. 차량기지 경로는
캡처마다 새로 인덱싱해 여러 노선이 찾는 동일 구간의 첫 검색 결과를 재사용한다.
다음 캡처에는 경로 편집과 순서 변경을 반영한다.

이름·색상·운영사·공개 정책·타임스탬프는 매번 새로 읽는다. 차량 500ms, 도착 정보 2초,
정적 자료 30초 갱신과 플랫폼별 도착 조회 128건·역별 표시 8건을 유지한다.
`useThreadedSimulation` 설정, 시뮬레이션과 저장, Core 의존성도 변경하지 않았다.

| 합성 입력과 측정 항목 | 이전 | 변경 후 |
| --- | ---: | ---: |
| 곡선 48개·공유 노선 4개: 좌표 계산 호출 | 24,096회 | 첫 캡처 12,000회, 변경 없는 다음 캡처 0회 |
| 같은 입력의 곡선 처리 커널 중앙값 | 11.066ms | 재사용 상태 0.215ms |
| 차량기지 500구간·250정차역·공유 노선 4개: 경로 항목 읽기 | 250,992회 | 998회 |

출력에 들어가는 좌표 수는 24,096개로 같다. 곡선의 모든 shape, 음수 좌표, 경사,
부분 구간, 캐시 퇴출, 같은 ID의 형상 교체, 정책·역 이름 변경, 반복 정차역과 무효한
첫 경로의 JSON·검색 결과를 비교했다. Java 검사 147개, 렌더링 8개, 믹스인 8개,
조명 호환성 3개, 웹 검사 42개가 통과했다. 구현·캐시 수명에 대한 독립 코드 검토도 마쳤다.
상세 동작은 [교통 API 안내](../Minecraft-Transit-Railway/docs/transit-api.md)에 있다.

위 숫자는 합성 입력의 작업 수와 로컬 커널 실행시간이다. 운영 월드의 전체 틱 시간,
서버 TPS, rx 또는 장애 횟수의 개선율로 환산할 수 없다. 특히 **Core 도착 응답 생성과
기본 단일 스레드 시뮬레이션의 자동 저장 비용은 남아 있다.** 정적 메타데이터 생성과
JSON 전송 비용도 계속 발생한다.

## 명령 없이 작동하는 자동 진단

`minefed-diagnostics` 1.1.1을 공개 MIT 서버 전용 모드로 등록하고 통합 브랜치에
병합·push했다. 클라이언트에는 설치하지 않는다. 기본 동작은 진단이며 게임 상태를
복구·변경하지 않고 외부에 업로드하지 않는다. 설정과 수집 파일의 정확한 의미는
[진단 모드 README](../minefed-diagnostics/README.md)를 기준으로 한다.

서버 시작 시 감시와 순환 기록을 자동 시작한다. 장애가 발생한 뒤 명령을 입력하거나
외부 스케줄러를 시작할 필요가 없다. 기본 감지 조건은 다음과 같다.

| 조건 | 수집 요청 시점 |
| --- | --- |
| 서버 틱 정지 | 첫 틱 시작 이후 마지막 틱 완료로부터 1초 경과 |
| 지속적인 느린 틱 | 완료된 100틱의 평균 작업 시간 75ms 이상 |
| 감시 스레드 지연 | 예상 기상 시각보다 1초 이상 지연 |
| 청크 작업 지연 | 작업이 20초 이상 끝나지 않음 |
| 청크 전송 진전 없음 | 대기 청크가 있으면서 배치 준비·ACK 등 관측된 진전이 10초간 없음 |

최근 **120초 / 최대 32MiB 순환 JFR**과 **2초 간격 OS/JVM 지표**를 유지한다.
이상 감지 시 별도 작업 스레드에서 JFR과 전체 스레드 덤프·직전/현재 지표를
`logs/minefed-diagnostics/captures/`에 같은 이름의 `.jfr`와 `.txt`로 기록한다.
모든 자동 수집 원인은 **5분 공통 간격 제한**을 공유하고 동시에 한 건만 대기·실행한다.
완료 파일은 최신 **8세트 및 합계 512MiB** 이내로 보관한다.

순환 기록은 초기 기동 직후 짧고, 덤프가 늦어지면 오래된 자료가 기록 범위 밖으로
밀릴 수 있다. JFR의 청크 단위 기록 때문에 32MiB는 정확한 바이트 상한이 아니며
덤프 중 임시 파일 공간도 필요하다. JFR을 사용할 수 없더라도 텍스트 수집은 시도한다.
Linux에서는 `/proc`·PSI·cgroup v2 지표를 읽고, Windows에서는 JVM 지표와 Linux 지표의
사용 불가 상태를 기록한다. 지표 누락을 정상적인 0으로 해석하지 않는다.

100틱은 실제 시간 대신 완료된 틱 수를 기준으로 한 겹치지 않는 창이다. 틱 사이 정상
대기는 제외하며 창 경계의 짧은 지연은 평균에 희석될 수 있다. 첫 틱 이전 월드 로딩은
틱 정지 감시 밖이다. **JVM 또는 호스트 전체가 멈추면 내부 수집기도 실행할 수 없다.**
재개 후 감시 스레드 지연을 기록할 수 있으나, 전원 장애·강제 종료 전에 파일 쓰기가
끝나지 않은 경우까지 보장하지 않는다.

감시 지연만으로 GC·호스트 정지·CPU 제한 중 원인을 단정할 수 없고, 청크 전송 훅은
실제 소켓 전송 성공을 증명하지 않는다. JFR·스택·OS 지표와 `ticks behind` 경고 시각을
함께 비교해야 한다. JFR·스레드 덤프·파일 쓰기의 진단 비용도 존재한다.

### 자동 진단 검증

다음 기동·JFR·Mixin 결과는 원래 1.1.0 JAR의 검증 기록이다.

- Java 17 빌드와 36개 검사를 통과했다. 실제 JFR 생성·읽기, 공통 수집 간격,
  보관량, 중단된 임시 파일 정리, 관측 실패 격리, 청크 전송 진행과 예외 정리를 확인했다.
- 격리된 Minecraft 1.20.4 / Fabric Loader 0.18.4 서버를 Java 21에서 기동했다.
  Vanilla와 Lithium `0.12.1+git.532b9c9` 양쪽에서 첫 틱에 1.8초 지연,
  이후 40틱에 각 90ms 지연을 넣었다. 시험 설정은 `slowTicks.window=20`,
  `capture.cooldownMs=10000`이며 나머지 수집 기본값을 사용했다.
  각 서버가 명령 없이 두 수집 세트를 생성했고 정상 종료했다. 비서버 스레드의 실제
  청크 요청을 완료했으며 진입·종료 훅과 `Internal errors: 0`을 확인했다.
- 두 서버의 JFR 네 파일을 `jfr summary`로 읽었다. 느린 틱 기록에는 `minefed.TickWindow`
  이벤트가 있었으며, 초기 환경 변수·시스템 속성·JVMInformation 이벤트는 0개였다.
  다른 동시 JFR 녹화가 있을 때까지 이벤트 제외를 보장하는 검사는 아니다.
- 배포본 `20261014150849`의 서버 모드에 이번 네 JAR을 적용한 **71개 모드**의
  Mixin audit를 실제 Knot 서버 환경에서 통과했다. 내보낸 변환 클래스에서 틱·배치·ACK 훅과
  Lithium 비서버 스레드 래퍼의 호출을 확인했다. 메인 스레드 청크 캐시 적중 경로에는
  진단용 배열·박싱이 추가되지 않았다. 이 검사는 전체 운영 월드의 플레이 검증은 아니다.
- 새 모드의 라이선스·JAR 메타데이터·서버 전용 선택, 네 소스의 라이선스 및 중첩 소스
  고정값과 빌드 계획을 검증했다. 릴리즈 입력 도구 검사 17개도 통과했다.

1.1.1에서는 [GitHub Actions 실행](https://github.com/minefed/mods/actions/runs/39008669933)에서
드러난 보관 순서 문제를 수정했다. 검사는 합성 단조 시각으로 수집 간격을 진행하므로
실제 파일명 시각이 같은 밀리초에 겹칠 수 있었고, UUID 사전순에 따라 최신 수집이
지워질 수 있었다. 정상 운영의 최소 10초 수집 간격에서는 이런 연속 수집이 일반적으로
발생하지 않지만, 시스템 시계 역행은 실제 서버에서도 파일명 순서를 바꿀 수 있다.
파일명 시각을 단조 증가시키고 재시작 시 소유한 기존 파일의 최대 시각에서 순서를
이어받는다. 보고서 본문에는 실제 감지·수집 시각을 기록하며 틱 처리·수집 간격은 유지한다.
같은 밀리초·시계 역행·재시작 회귀 검사 3개를 추가해 Java 17의 검사 39개와 빌드를
통과했다. 독립 검토에서 지적 사항은 없었다. 새 GitHub Actions 결과는 확인 중이며,
이 기록은 성공을 미리 선언하지 않는다. 실제 서버 기동 검사는 이번 수정으로 재실행하지 않았다.

Windows 한글 기본 임시 경로에서 JDK 17/21의 빈 JFR 덤프를 재현했고, 테스트 JVM에
ASCII 임시 디렉터리를 지정해 해결했다. Linux `/proc`·cgroup 읽기는 파일 fixture로
검증했으며 실제 운영 Linux 컨테이너의 수집과 운영 부하는 아직 검증하지 않았다.

## 배포 상태와 다음 확인

이 작업에서는 운영 서버의 파일·설정·설치 JAR를 바꾸거나 재시작하지 않았다.
[저장소 작업 지침](../AGENTS.md)에 따라 서버 설치·업로드·재시작은 별도 요청으로 수행한다.
적용 이후 장애 시각의 자동 수집 세트와 같은 시간대 서버 로그를 함께 확인해야
남은 MTR 계산·저장, 청크 대기, 호스트 자원 문제, 클라이언트·네트워크 문제를 구분할 수 있다.
기존 [외부 수집 도구](../tools/server-stall-capture/README.md)도 독립적인 수집 수단으로 남아 있다.
