# 배포 다운로드 오류 수정과 차량 렌더링 추가 개선

## 확인한 배포 실패

[실패한 GitHub 실행](https://github.com/minefed/mods/actions/runs/37376898848)의
[build 로그](https://github.com/minefed/mods/actions/runs/37376898848/job/111988181908)에서
MTR는 정상 빌드됐다. 이후 `mc-realtime`의 Gradle 8.11.1 배포판 다운로드가
HTTP 500으로 실패했고, 약 45분간 진행된 전체 빌드가 배포 전에 중단됐다.
소스 컴파일 오류나 MTR 테스트 실패가 원인이 아니었다.

`build_modpack.py`는 wrapper 다운로드에서 확인되는 HTTP 429/5xx와 명시적
연결·읽기 시간 초과만 최대 세 번 시도한다. 대기 시간은 2초와 4초다.
Gradle 자체가 시작된 뒤의 오류, 컴파일·테스트 실패, 체크섬·인증·404 오류는
즉시 실패로 처리한다. 같은 단계만 재시도하며 기존 잠금, 도구 지문 확인,
실패한 소스의 바이너리 대체 금지 정책을 유지한다.

첫 시도부터 각각의 로그와 마지막 시도 로그를 보존한다. GitHub에서는 실패한
소스의 Gradle 로그만 별도 진단 artifact에 3일간 남긴다.
[빌드 실패 처리 안내](BUILDING.md#결과물과-실패-처리)를 참고한다.

## 추가 렌더링 개선

MTR `b63de38863bfb9afd8a04bf983a8dc65fa66146c`는 차량 렌더링 호출 시작 때
확인한 그림자 패스 여부를 동기 실행되는 각 차량 칸의 소리 조건에서도 재사용한다.
이 조건까지 도달하는 차량 칸이 N개라면 기존 N+1회 검사를 1회로 줄인다.
원본 검사는 호출할 때마다 현재 스택 추적을 생성하므로 중복 객체 생성도 없앤다.

값은 지역 변수이며 다음 렌더 호출에서 다시 조회한다. 그림자 패스와 일반 패스의
전환을 매번 반영하고, 지연 실행되는 선로 콜백의 검사는 유지한다.
[동작 보존 근거](../Minecraft-Transit-Railway/docs/vehicle-shadow-check.md)에
동기 콜백 경로와 최종 JAR 바이트코드 확인 방법을 기록했다.

별도로 검토한 StackWalker 전면 교체는 합성 검사에서 할당량이 증가해 채택하지
않았다. 이번 추가 수정의 인게임 FPS는 새로 측정하지 않았으며,
[앞선 장비 측정](CLIENT_DEVICE_PERFORMANCE_2026-10-06.md)의 결과를 새 JAR의
측정값으로 바꾸지 않는다.

## 검증과 로컬 적용

- 빌드 도구 테스트 65개 통과: 신규 재시도 검사 11개와 기존 잠금·취소·무결성 검사 포함.
- 병렬 빌드 테스트 10개 중 8개 통과, Windows에서 POSIX 신호 검사 2개 건너뜀.
- 릴리즈 제어 테스트 13개, 릴리즈 입력 테스트 17개와 actionlint 1.7.12 통과.
- MTR Java 17 테스트 89개, 선로 8개, Mixin 8개, 조명 3개 통과. `remapJar` 생성 성공.
- 기존 수정본과 JAR 내부 항목을 비교해 추가·삭제가 없음을 확인했다. 차이는
  `RenderVehicles`와 그 내부 클래스 3개뿐이며 리소스와 의존 라이브러리는 동일하다.
- 게임이 종료된 상태에서 이전 MTR JAR를 백업하고 새 파일을 로컬 `client` 프로필에
  설치했다. 이번 교체에서는 게임 옵션과 display JAR를 변경하지 않았다.

전체 소스 커밋, 추적 브랜치, Minecraft/로더 호환성, JAR 해시와 MIT 고지는
[수정본 명세](../inventory/client-release-followup-2026-10-06.json)에 기록했다.
운영 서버 파일 변경·업로드·재시작은 수행하지 않았다.
