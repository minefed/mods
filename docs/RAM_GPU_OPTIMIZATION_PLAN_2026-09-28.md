# 모드팩 RAM·GPU 최적화 조사와 제안 — 2026-09-28

[네트워크·FPS 최적화](OPTIMIZATION_PLAN_2026-09-28.md)에 이어, 클라이언트·서버의 **RAM(Java 힙과 네이티브 메모리)**과
**GPU 메모리·GPU 부하**를 더 줄일 수 있는 지점을 조사했다. 이 문서는 제안서다. 코드·운영 서버는 바꾸지 않았다.

## 조사 범위와 방법

- 대상은 최신 공개 릴리즈 `20260928191618`의 `client.mrpack`이다. SHA-256은
  `22c84e32d06c24b5173456a0bf1c0272d5266266d3d05f0460c93cfa491412b6`, 모드 JAR는 72개다.
  비교 기준으로 Mojang 공식 1.20.4 클라이언트 JAR를 함께 사용했다.
- **블록 아틀라스:** 모든 JAR와 동봉 리소스팩에서 블록 아틀라스에 들어가는 PNG를 추렸다. 대상은 `textures/block`·`textures/item`과
  각 모드 `atlases/blocks.json`의 추가 경로다. 모두 10,567개이며 애니메이션은 프레임 크기로 계산했다.
  아틀라스 크기는 바닐라 `Stitcher` 알고리즘을 그대로 옮긴 스크립트로 계산했다. 밉맵 제한 경고 문자열은 바닐라 클래스(`gem`)에서 확인했다.
- **소스 확인:** MTR, MSD, minefed-display, webstreamer, ModernFix 서브모듈을 읽었다.
  MCEF 2.1.6과 MTR에 번들된 Mappings 렌더 라이브러리는 JAR 바이트코드로 확인했다.
- 게임은 실행하지 않았다. 따라서 아래 수치는 **계산값 또는 코드 기반 추정치**다.
  실측값은 [2026-09-21 진단](PERFORMANCE_DIAGNOSIS_2026-09-21.md)의 기록뿐이다.
  당시 환경은 최대 힙 8 GiB, GC 후 사용량 약 3.3 GiB, AMD Ryzen 7 7730U 내장 GPU였다.
- **내장 GPU 환경의 의미:** 내장 GPU는 시스템 메모리를 VRAM으로 쓴다. 따라서 GPU 메모리를 줄이면 그대로 시스템 RAM 여유가 된다.

### 블록 아틀라스 상세

아틀라스 한 장이 현재 클라이언트에서 가장 큰 단일 GPU 메모리 항목이다.
City Craft 2048² 텍스처 한 장은 가드레일 한 개(높이 약 1.5블록)에 쓰인다. 모델 파일은 32×32 텍스처 기준으로 만들어져 있다(`texture_size: [32, 32]`).
64배 크기의 원본을 그대로 쓰고 있는 셈이다.

A에서 픽셀 수가 거의 절반으로 줄어도 아틀라스 한 변이 2의 거듭제곱으로 올림되므로 VRAM은 그대로다. 이 계산에서 8192×8192로 내려가는 경계는 `trash_bin_metal`까지 줄였을 때다.
실제 크기는 `latest.log`의 `Created: …x…x… minecraft:textures/atlas/blocks.png-atlas` 줄로 확인한다.
16384 한 변은 `GL_MAX_TEXTURE_SIZE`가 8192인 구형 GPU에서 아틀라스 생성 자체가 실패하는 크기이기도 하다. 따라서 줄이면 호환성도 좋아진다.

### 2단계 — 블록 아틀라스 (VRAM 최대 절감)

바이너리 전용 모드(PTS-Deco, ARR)의 텍스처도 다뤄야 하므로 방법 두 가지를 비교했다.

- **권장: `minefed-client-compat`의 로드 시점 처리.** 스프라이트를 읽을 때(`SpriteContents` 생성) 이미지를 바꾸는 선택적 믹스인이다.
  원본 에셋을 복사하거나 재배포하지 않고, 모든 모드에 같은 규칙을 적용한다.
- **대안: `compatibility/resource-fixes`의 텍스처 덮어쓰기.** City Craft·MSD·MTR은 MIT라 수정본을 배포할 수 있다.
  다만 고지 관리가 필요하고, PTS-Deco처럼 권리가 유보된 텍스처는 이 방법으로 처리할 수 없다.

| 2-5 | MTR 에스컬레이터 애니메이션(320×5120, 16프레임, 1틱 간격): 크기를 줄이는 것은 화면 변화이므로 별도로 판단한다. | 줄이면 변화 | 현재 두 장이 약 16.7 MiB 네이티브를 쓰고, 보일 때 매 틱 약 10 MB/s를 업로드한다. |

권장 조합은 2-1 + 2-2 + 2-3(City Craft만)이다. 이 조합으로 VRAM은 512 → 약 341 MiB, 네이티브 사본은 257 → 약 169 MiB가 되고 밉맵 4단계가 돌아온다.
밉맵을 켤지 여부(2-2)는 화면 품질 판단이다. 2-2 없이 2-1 + 2-3만 적용하면 VRAM은 256 MiB가 된다.

### 4단계 — 설정과 JVM (코드 변경 없음)

**클라이언트 JVM** (런처의 인스턴스 설정. mrpack에는 JVM 인자를 넣을 수 없으므로 [릴리즈 안내](RELEASING.md)에 권장값으로 적는다):

- **최대 힙:** 8 GiB 대신 약 **5~6 GiB**를 권장한다. GC 후 사용량 3.3 GiB의 약 1.5~1.8배다.
  내장 GPU 장비에서는 줄인 만큼 GPU가 쓸 시스템 메모리가 늘어난다. 1~2단계를 적용한 뒤 다시 측정한다.
- **G1의 유휴 메모리 반환:** `-XX:G1PeriodicGCInterval=30000`을 추가해 유휴 시 커밋된 힙을 운영체제에 돌려준다.
  `-Xms`는 작게 둔다. 게임 동작에는 영향이 없다.
- **표시 동기화:** [2026-09-21 진단](PERFORMANCE_DIAGNOSIS_2026-09-21.md)에서 확인한 대로 VSync 해제가 FPS에 가장 효과적이었다. 다만 화면 찢어짐이 생길 수 있다.

**ModernFix 옵션** (`config/modernfix-mixins.properties`):

| 옵션 | 기본 | 판단 |
| --- | --- | --- |
| `mixin.perf.dynamic_sounds` | 켜짐 | 유지한다. MTR의 스트리밍하지 않는 소리 1,701개는 PCM으로 풀면 약 193 MiB다. 이 옵션이 쓰지 않는 소리를 비우므로 효과가 크다. |
| `mixin.perf.deduplicate_location` | 꺼짐 | 후보다. `ResourceLocation`의 네임스페이스·경로 문자열을 중복 제거한다. 모델 JSON 7.7만 개 규모라 힙 절감 여지가 있다. 시작 시간이 늘 수 있으므로 힙 히스토그램으로 전후를 비교한 뒤 채택한다. |
| `mixin.perf.clear_mixin_classinfo` | 꺼짐 | 보류한다. 로딩 후 Mixin 클래스 정보를 비워 힙을 줄인다. 늦게 로드되는 클래스에 믹스인을 적용하는 모드가 깨질 수 있다. |
| `mixin.perf.dynamic_resources` | 꺼짐 | 계속 제외한다. Fusion·Continuity와 알려진 문제가 있다([운영 설정](SERVER_TUNING_2026-09-28.md)). |

**서버:**

- **WorldEdit:** 기본값은 `history-size=15`, `max-changed-blocks=-1`이다. 대규모 편집의 되돌리기 기록 15개가 모두 힙에 남으므로 GB 단위가 될 수 있다.
  운영 방식에 맞춰 `default-max-changed-blocks`나 `history-size`를 정한다. 이는 편집 한도가 바뀌는 운영 결정이다.
- **BlueMap·Chunky:** [운영 설정 안내](SERVER_TUNING_2026-09-28.md)대로 렌더 스레드 수와 사전 생성 동시 작업 수를 조절한다. 이 둘은 메모리 사용에도 직접 영향을 준다.

### 5단계 — 모드 추가 후보 (별도 결정·검증 필요)

아래 두 모드는 1.20.4 Fabric용 배포본이 있다. 라이선스와 MTR·minefed-display·Sodium 0.5.8과의 호환성을 확인하기 전에는 추가하지 않는다.

- **ImmediatelyFast:** 텍스트, 지도, HUD, 표지판처럼 즉시 모드로 그리는 요소를 묶어 드로 콜을 줄인다. 표지판과 글자가 많은 MTR·mishanguc 장면에 유리하다.
- **Entity Culling:** 벽 뒤의 엔티티·블록 엔티티를 비동기 레이 판정으로 건너뛴다. PFM, TrafficCraft 신호등, 표지판 블록 엔티티가 밀집한 도시 장면에서 GPU·CPU를 줄인다.
  다만 `rendersOutsideBoundingBox`를 쓰는 디스플레이는 예외 설정이 필요하다.

## 검증 방법

- **아틀라스:** `latest.log`에서 다음 두 가지를 확인한다.
  - `Created: …x…x… minecraft:textures/atlas/blocks.png-atlas`: 크기와 밉맵 단계
  - `limits mip level` 경고: 남아 있으면 안 된다
- **화면 동일성:** [크리에이티브 인벤토리 감사](../tools/creative-inventory-probe/README.md)와 고정 월드 장면 스크린숏으로 전후 픽셀을 비교한다. 2-1은 차이가 0이어야 한다.
- **메모리:**
  - `jcmd <pid> GC.class_histogram`: 힙 구성
  - 프로세스 RSS와 힙의 차이: 네이티브 메모리
  - 작업 관리자의 GPU 전용·공유 메모리
  - Chromium 하위 프로세스 수
  - 같은 경로를 30분 반복한 전후 비교로 누수 해소를 확인한다(1단계).
- **기존 회귀 검사:** MTR은 `verifyRailRendering`·`verifyMixinCompatibility`, minefed-display는 `verifyDisplayOcclusion`을 다시 실행한다.

## 부수 발견

- minefed-display 최대 크기(32블록 × 400 px = 12,800 px)는 `GL_MAX_TEXTURE_SIZE`가 8192인 GPU의 한도를 넘는다. 해상도 변경은 기존 원칙상 제외 항목이므로 정확성 위험으로만 기록한다.
- webstreamer JAR(77 MB)는 5개 플랫폼용 FFmpeg 네이티브를 모두 포함한다. 실행 시에는 해당 플랫폼 것만 로드하므로 RAM 영향은 작고, 다운로드 크기에만 영향이 있다.
- MTR의 `hasOptimizedRendering()`은 항상 참이다. 그래서 선로·오브젝트 모델과 함께 보관하는 `DynamicVehicleModel`은 실행되지 않는 분기에서만 쓰인다. 제거하면 힙이 줄어든다.
