# MTR 3D 선로 렌더러 최적화 — 2026-09-21

현재 모드팩의 Minecraft 1.20.4 / Fabric Loader 0.18.4 / Java 17 클라이언트를 대상으로
3D 선로의 반복 좌표 계산, 행렬 변환, 렌더 작업 등록을 줄였다. 모델·텍스처와 조명 갱신은 유지한다.
첫 수정의 실제 개선이 작아, 실제 업로드 모델의 경계를 이용한 화면 밖 조각 제외를 두 번째 수정으로 추가했다.

**동일 승강장·시점·설정에서 안정화 후 평균 22.2~24.7 FPS → 41.0~50.0 FPS,
프레임 시간 p95 85.9~86.4ms → 26.2~36.1ms로 개선됐다.**
최종 JAR를 실행 중인 프로필에 설치했다. 3D 선로는 켜져 있으며,
VSync를 복원했을 때 별도의 대기 병목이 확인되어 최종 설정은 VSync 꺼짐으로 두었다.

## 변경한 실행 경로

전체 흐름은 `MinecraftClientData.RailWrapper` → `RenderRails.render()`의 가림 판정과 스타일 선택
→ Core `RailMath.render()`의 구간 생성 → `RailResource` / `StoredModelResourceBase`
→ `MainRenderer` 렌더 큐 → `OptimizedRendererWrapper` → 번들 Minecraft-Mappings의
`OptimizedRenderer` / `BatchManager` / GPU 제출이다.

기존에는 같은 선로 조각마다 매 프레임 좌표·방향·경사를 계산하고, 변환 목록과 람다를 만들었다.
렌더 콜백에서 행렬 스택을 복사한 뒤 위치·법선 행렬을 각각 세 번 회전했다.
실제로 최적화 렌더러의 큐가 소비하는 것은 위치 행렬의 복사본뿐이었다.

- `RailGeometryCache`: RailMath 객체, 모델 반복 간격, Y 오프셋, 반대 방향 여부로 정적 배치를 캐시한다.
  최대 131,072개 조각 / 2,048개 항목으로 제한한다. 큰 선로와 매 프레임 재생성하는 미리보기는 기존 경로를 사용한다.
- `RailModelGeometry`: 중점 좌표와 회전 행렬을 한 번 계산한다. 월드 좌표에서 카메라 좌표를
  double 정밀도로 뺀 뒤 float 행렬로 변환해 먼 좌표의 정밀도를 보존한다.
- `RailRenderView`: 기존 수평 렌더 거리·32블록 근접 범위·카메라 방향 판정을 유지하면서
  조각별 임시 벡터와 반복 삼각함수 계산을 없앤다.
- `RenderRails`: 선로/스타일당 모델 캐시를 한 번 조회하고 렌더 콜백 하나를 등록한다.
  행렬 스택도 묶음당 한 번 저장한다. 조각마다 캐시한 회전 행렬을 적용하고 현재 블록·하늘 조명을 조회한다.
- 클라이언트 전용 `GraphicsHolderRailMatrixMixin`: Fabric/Forge의 위치 행렬을 연결한다.
  이 경로에서 사용하지 않는 법선 행렬 회전과 조각마다 발생하던 스택 복사를 생략한다.
- 월드 교체, 데이터 초기화, 연결 종료, 리소스 재로딩에서 캐시를 비운다.
  캐시에는 GPU 모델 핸들, 월드 객체, 조명 값, 가시성 결과를 저장하지 않는다.
- `RawModelBoundsMixin` / `OptimizedModelBoundsMixin`: 실제 업로드 정점에서 모델 원점 기준
  보수적인 구 경계를 산출한다. Blockbench와 OBJ/MQO 변환 결과를 모두 포함하고,
  결합 모델은 가장 큰 경계를 사용한다. WeakHashMap은 GPU 객체를 계속 붙잡지 않는다.
- `RailModelFrustum`: 실제 셰이더와 같은 projection × modelView × base 행렬로 화면 영역을 구한다.
  모델 전체가 화면 밖일 때 조명 조회와 GPU 제출 등록을 건너뛴다. 크기를 알 수 없는 모델,
  잘못된 경계·투영은 표시를 유지하며, 셰이더 그림자 패스는 기존 판정을 유지한다.

2D 선로·신호·방향 화살표·노드·가공전차선의 기존 경로와 MSD의 `RenderRails.render()` HEAD 주입은 유지한다.
묶음 처리는 CPU의 작업 등록을 줄이고 화면 영역 검사는 화면 밖 모델의 GPU 제출을 생략한다.
화면에 보이는 모델의 메시·텍스처·조명·드로 방식은 유지한다.
상세 설계와 각 단계의 분석은 [MTR 문서](../Minecraft-Transit-Railway/docs/rail-rendering-optimization.md)에 기록했다.

## 실제 게임 비교 방법

재접속한 원래 위치 `(-429.5, 68, -51.5)`는 지면 아래의 좁은 공간이었다.
재접속 이후의 가림 판정으로 이곳에서는 기존 버전도 50.6 FPS가 나와,
앞선 진단에서의 16~24 FPS와 직접 비교할 수 없었다.
가까운 승강장으로 이동해 실제 3D 선로가 보이는 장면에서 새 기준을 수집했다.

비교 좌표는 **(-590.5, 70, 52.5), yaw 90°, pitch 20°**다.
854×480, 렌더 거리 12, 시뮬레이션 거리 12, FPS 제한 120,
기본 3D 선로 켜짐, VSync 꺼짐 조건을 동일하게 사용한다.
F3+L의 약 10초 프레임 기록을 반복하고, 각 JAR에서 45초 JFR profile 기록을 수집한다.
프레임 수 / 기록 시간으로 FPS를 산출하며 서버 TPS로 해석하지 않는다.
JFR과 OS 프로세스의 원시 자료는 로컬에만 보존한다.

기존 두 기록의 합산 FPS는 23.45, 최종 안정화 세 기록은 45.12로 **약 1.92배**다.
다만 서버 월드의 열차·엔티티 상태와 JIT 상태는 시간에 따라 달라지므로 보장 수치가 아니다.
초기 기록의 7.5 FPS 저하는 숨기지 않고 위에 포함했다. 최초 JFR과 겹친 재실행 초기의 기록이며,
같은 JFR 설정으로 다시 측정한 02:29 기록에서는 재현되지 않았다. 이 일시 저하의 원인은 확정하지 못했다.
안정화 후 비교값과 초기 예외를 분리하며, 서버 TPS나 모든 지역의 성능으로 일반화하지 않는다.

원래 VSync 켜짐을 복원한 별도 기록(02:37:19)은 **27.4 FPS**, p95 57.0ms,
최장 97.6ms, 100ms 초과 0회였다. `updateDisplay` 대기가 프레임 프로파일의 **51.96%**를 차지했다.
따라서 코드 최적화와 별도로 최종 VSync는 껐다. 원본 `options.txt`와의 키별 비교에서
변경은 `enableVsync: true → false` 하나뿐이며, `mtr.json`과 `sodium-options.json`은 원본과 해시가 같다.

기존 버전의 45초 JFR에서는 렌더 스레드 Java 실행 샘플 896개 중 619개가
`MainRenderer.render`, 160개가 선로 회전 람다를 통과했다. 서로 겹치는 스택 비율이다.
렌더 스레드 할당 카운터 증가량은 약 219.0 MiB/s였고 GC 정지 합계는 96.8ms,
최장은 19.3ms였다. MTR 가림 판정 작업 스레드의 Java 샘플은 2,939개였다.

1차 수정은 할당을 **151.8 MiB/s**로 줄였지만 플레이 성능 개선은 충분하지 않았다.
새 JFR에서 조각별 조명 조회와 `BatchManager.queue`가 여전히 큰 비용을 차지했다.
따라서 1차 수정만으로 해결됐다고 결론 내리지 않고 2차 화면 영역 검사를 추가했다.

최종 안정화 JFR은 45초 기록이며 다음을 확인했다.

- 선로 묶음 콜백이 포함된 렌더 스레드 Java 샘플 비중은 1차 수정 **317/921(34.4%)**에서
  2차 수정 **155/1,076(14.4%)**로 줄었다. 이는 샘플 스택 비율이며 벽시계 시간 비율이나 서로 더할 수 있는 비율이 아니다.
- JVM 전체 CPU 사용률 평균은 기존 30.0% → 최종 20.8%였다(논리 프로세서 전체 기준).
- 렌더 스레드 할당 카운터는 최종 201.4 MiB/s였다. 기존 219.0 MiB/s보다 낮지만,
  최종 버전이 초당 더 많은 프레임을 처리하므로 1차 수정의 151.8 MiB/s와 단순 우열 비교하지 않는다.
- GC 정지 합계는 기존 96.8ms → 최종 47.3ms, 최장은 19.3ms → 16.7ms였다.
- 남은 비용으로 `RenderVehicleHelper.canOpenDoors`가 렌더 스레드 Java 샘플 281/1,076(26.1%)에,
  가림 판정 작업 스레드가 Java 샘플 3,470개에 나타났다. 이들은 이번 3D 선로 변경으로 수정하지 않았다.

실제 게임에서 반대 방향 시점, 플랫폼 이동, 가까운 선로를 내려다보는 시점을 확인했다.
레일과 침목이 유지됐고, 클라이언트 MTR 리소스 재로딩은 **2.67초 / HTTP 200**에 완료됐다.
이후 50.0 FPS 기록에서 50ms를 넘는 프레임은 없었다. 빛 값은 프레임마다 조회하는 구조를 유지했으며,
주야간 전환·외부 셰이더 그림자 패스·모든 커스텀 선로를 전수 실게임 검증한 것은 아니다.

## 검증과 버전

- 선택한 회귀 테스트 **55개 통과**. 실제 Minecraft MatrixStack 결과와 곡선·경사·뒤집힘·
  반복 간격·월드 경계 좌표를 대조했다. 카메라 10,000개 사례와 거리 경계, 캐시 교체·삭제·용량 제한도 검사했다.
- 선로 전용 검사 **8개 통과**(회귀 테스트와 중복 포함). 화면 경계·근거리 절단면·큰 모델·
  잘못된 데이터와 20,000개 셰이더 공간 정점 사례를 비교해 화면 안 정점이 제외되지 않음을 확인했다.
- 배포 JAR Mixin 검사 **5개 통과**. 실제 번들 행렬 필드와 remap 결과, 행렬 복사 계약,
  기존 Loader 0.18.4/MixinExtras 호환성을 확인했다.
- Fabric 배포 JAR 빌드 및 Forge 1.20.4 컴파일 통과. Forge는 `setupFiles` 후 컴파일했고,
  이 Windows 환경에서는 임시 init 스크립트로 Java 소스 인코딩을 UTF-8로 지정했다.
  Forge 게임 실행 시험은 하지 않았다.
- 원본/신규 JAR의 모든 ZIP 항목을 SHA-256으로 비교했다. 추가 13개 클래스와 관련 렌더/초기화
  클래스·Mixin 설정만 달랐고, 삭제된 항목은 없었다. 모델·텍스처·번들 의존성·라이선스 내용은 일치했다.

`scripts/mods.py verify --sources`로 70개 기록 아티팩트와 소스 pin을 확인했다.

클라이언트 프로필 `ModrinthApp/profiles/client`에 신규 JAR를 설치하고 해시를 확인했다.
원본은 해당 프로필의 `minefed-backups/rail-optimization-20260921-014548/`에 보관했다.
1차 수정 JAR와 설정도 `minefed-backups/rail-frustum-20260921-021722/`에 별도 보관했다.
설치 출처는 프로필의 `MINEFED-RAIL-OPTIMIZATION.json`, 측정 원본은 저장소의
`.cache/performance/20260921-rail-optimization/`에 있다. 운영 서버의 파일 변경·업로드·재시작은 수행하지 않았다.

원본으로 복구할 때는 클라이언트를 종료한 뒤 첫 백업 폴더의 `fabric-4.0.5.jar`를
프로필 `mods/`로 복원한다. VSync만 되돌릴 때는 게임의 비디오 설정에서 수직 동기화를 켜면 된다.
최종 게임은 위 비교 승강장에 접속한 상태이며 디버그 표시와 측정 메뉴는 닫았다.
