# 1차 성능 개선 구현과 검증 — 2026-10-12

Minecraft **1.20.4 / Fabric / Java 17**을 대상으로 차량 텍스처 공유,
Oritech GUI 전송 축소, MSD 불변 응답 처리와 안내판 파생 데이터 캐시를 구현했다.
운영 서버 파일·설정·업로드·재시작과 게임 설치 폴더는 변경하지 않았다.

## 구현한 변경

| 저장소 | 변경 | 보존한 동작·외관 |
| --- | --- | --- |
| resourcepack | A1000의 아틀라스·트레일러 라벨 참조 10곳을 바이트가 같은 Mistilteinn 텍스처 ID로 공유 | 차량 등록 6개, 모든 PNG·BBMODEL·UV·기하와 저작 파일 유지 |
| Oritech | 프레임 기계 GUI 상태를 해당 기계의 실제 Basic 메뉴 사용자에게만 전송. energy/capacity/progress가 같으면 생략 | 열기·재열기 초기 스냅샷, 여러 사용자, 기존 패킷 형식·수신기·물리·레시피·이동·인벤토리 렌더 경로 유지 |
| MSD | 객체 페이로드·제거·미동기화 객체 변경이 없는 keep-only 응답에서 그래프·래퍼 재구축 생략 | 객체 추가·동일 ID 교체·삭제·reset/update/delete는 기존 sync 실행 |
| MSD | 야마노테 안내판의 노선 이름·색상 목록과 선택 플랫폼 순서를 제한된 캐시에 저장 | 기존 중복 색상 선택·정렬·번역 구분·연결 역 처리와 매 프레임 텍스처 조회·그리기 유지 |

Oritech의 기존 `isActivelyViewed()`는 플레이서 인벤토리 패킷의 조건으로도 사용된다.
그 계약을 그대로 두고 GUI 수신자 판별을 별도로 구현했다. 슬롯 선택만 표시하는
인벤토리 프록시 화면에는 새 GUI 상태 패킷을 추가하지 않았다. 메뉴 객체·기계 객체의
동일성으로 재열기와 교체를 구분하며, 닫힘·추적 종료·접속 및 차원 변경·기계 제거 때
관람자 스냅샷을 정리한다.

MSD는 공개 객체 집합의 크기와 ID 맵의 객체 동일성도 확인하여 미동기화 로컬 추가·삭제·교체를
빠른 경로에서 제외한다. 안내판 캐시는 데이터·역의 약한 참조, 선택 ID의 값 스냅샷,
동기화 revision과 노선/플랫폼 모드를 구분한다. MTR sync RETURN, 접속·해제와 데이터 교체에
무효화하며 최대 256개 항목과 65,536 weight 단위로 제한한다. weight는 선택 원소·결과 ID·문자와
고정 비용을 합친 계산 단위이며 실제 힙 바이트 상한이 아니다. 텍스처·그래픽 상태는 저장하지 않는다.

## 확인한 작업량 감소

- **텍스처:** 두 차량군을 동시에 로드하면 서로 다른 텍스처 ID 6개 → 4개.
  기본 레벨 RGBA 크기 합은 192 MiB → 112 MiB로 **80 MiB** 줄어든다.
  이는 이미지 크기 계산이며 실제 VRAM 측정값이 아니다. 드라이버·밉맵·수명 정책과
  동시에 상주하는 텍스처에 따라 실제 차이가 달라진다.
- **Oritech:** 추적 사용자 10명·가장 가까운 메뉴 사용자 1명·불변 상태 20 tick의
  테스트 조건에서 기존 예상 수신자 전달 200회 → 열기 스냅샷 1회.
  상태가 변하는 20 tick은 업데이트 전달 200회 → 20회. 실제 네트워크 바이트 측정은 아니다.
- **MSD 응답:** 초기 sync 뒤 불변 응답 1,000개에서 추가 그래프 재구축 0회.
  패킷 데이터와 수신 요청량은 변경하지 않았다.
- **MSD 안내판:** 두 모드의 최초 파생 계산 합계 2회 뒤 1,000 warm frame에서 추가 계산 0회.
  프레임별 캐시 조회·선택 값 비교와 기존 텍스처 조회·그리기는 계속 수행한다.

이번 묶음은 서버 GUI TX와 클라이언트 중복 텍스처·반복 계산·임시 할당을 줄인다.
서버 RX, GPU 사용률, CPU/RAM 실사용량, 프레임 시간의 개선 비율은 측정하지 않았다.
해상도·시야 거리·셰이더·게임 옵션을 바꾸지 않았다.

상위에서는 원격 전체 해시를 확인한 뒤 저장소별 gitlink와 lock을 별도 커밋으로 갱신했다.

## 검증 범위

- **resourcepack:** 차량 등록 6개의 의미 동등성, 모델 참조 26개와 내장 이미지의 동일성,
  나머지 추적 파일 316개의 해시 불변, 런타임 JSON 파싱을 확인했다. 실제 MTR
  `ModelTextureEvictor` 코드로 공유 키·사용 갱신·유휴 제거·재사용 18개 검사를 통과했다.
- **Oritech:** 실제 생산 tick/opening/menu와 `PlacerBlockEntity.updateNetwork()`를
  플랫폼 대역에서 실행하여 13개 시나리오·96개 검사를 통과했다. 실제 Fabric 의존성
  바이트코드에서 메뉴 설치 → opening writer 순서를 확인했다. Java 17로
  `:verifyFrameGuiSync`와 실제 Minecraft/Fabric 의존성을 사용한 `:remapJar` 빌드를 완료했다.
- **MSD:** 실제 core 데이터·fastutil·생산 응답·클라이언트 래퍼의 26개 계약 검사와 실제 MTR core 객체를
  사용한 안내판 검사 4,812개를 통과했다. 200개 무작위 데이터 구성을 포함해 기존 이름·색상·순서와
  비교하고 선택 수정·동기화·데이터/역 교체·LRU·weight·초과 항목 우회·예외를 확인했다.
  기존 텍스처 조회와 그리기 경로는 고정한 이전 소스와 비교했다.
  기존 Fabric/생성 Forge trace 각각 렌더 비교 937회·조명 비교 24회·검사 6,757개와
  실제 Fabric LightType 동일성 검사를 통과했다. Fabric 전체 소스 컴파일·remapJar 및
  신규 생산 파일 5개의 생성 Forge parity를 확인했다. Forge 전체 JAR는 빌드하지 않았다.
- **상위 도구:** 저장소 의존성 정책 검사 2개, 도구 테스트 226개(환경에 따른 생략 12개),
  변경된 빌드 레시피 관련 테스트 65개와 워크플로 YAML 파싱을 통과했다.
  최종 빌드 계획과 `mods.py verify --sources`도 통과하여 기준본 아티팩트 70개와
  전체 소스 gitlink·lock·로컬 HEAD 및 하위 작업 트리의 일치를 확인했다.
- **산출물:** 외부·내장 JAR CRC, SHA-256, Fabric ID/버전/의존성, 변경 클래스의 Java 17
  바이트코드, 기존 라이선스 고지 보존과 검증 클래스 미포함을 확인했다.
  Oritech 1,144개와 MSD 493개 리소스의 목록·바이트가 각각 이번 작업 직전 소스 pin과 일치한다.

운영 기준본 JAR의 해시는 유지하고 이번 빌드 해시·크기·출처·호환성은
[산출물 기록](../inventory/phase1-optimizations-2026-10-12.json)에 별도로 남겼다.
JAR 비교 기준은 작업 전에 보존한 기존 로컬 빌드 출력이며 직전 pin을 새로 빌드한
기준본이라고 주장하지 않는다. 따라서 JAR 차이 목록에는 이전 변경이나 컴파일러 차이가
포함될 수 있으며, 이번 소스 변경 범위는 위 커밋의 diff로 확인한다. MSD의 과거 로컬 JAR와
리소스 51곳이 다르지만, 새 JAR의 모든 리소스는 이번 작업 직전 소스 pin과 바이트가 같다.

Oritech 본체는 해당 역사적 태그의 CC0-1.0, MSD 본체는 MIT 고지를 보존했다.
내장 의존성은 각각의 라이선스를 유지한다. 리소스팩 이미지는 Minefed 저작권 조건과
기존 게임 파일 배포 승인 범위를 유지하며 저작·디자인 자료의 공개를 추가하지 않는다.
JAR나 디자인 자료를 Git에 추가하지 않았다.

게임 연결 도구로 상태 조회를 시도했으나 unavailable을 반환했다. 이번 빌드로 게임을
기동하거나 OpenGL 화면, FPS·VRAM·CPU·RAM·실제 송수신량을 측정하지 않았다.
실제 외관 확인과 성능 비교는 같은 팩·JVM·월드·시점에서 별도 실행해야 한다.

재현용 검증 코드는 하위 저장소의 `Oritech/src/frameGuiVerification/`, MSD의
`verification/data-response/`, `verification/sign-derived/`와 기존 렌더 검증에 보존했다.
새 검사들은 상위 빌드 레시피에 포함하며 MSD의 Fabric check/build 및 Oritech CI에서도 실행한다.
