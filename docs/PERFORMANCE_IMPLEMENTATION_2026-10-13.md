# 2026년 10월 13일 성능 최적화 구현 및 검증

Minecraft 1.20.4 / Fabric Loader 0.18.4 / Java 17 실행 환경을 대상으로 한다. 이미지 원본과 기존 픽셀 변환 결과, 도착 정보의 내용과 순서를 유지하면서 중복 다운로드·검색·변환·출력 호출을 줄였다. 운영 서버 업로드와 재시작은 수행하지 않았다. 소스 고정값은 `inventory/mods.lock.json`, 신규 JAR 및 검증 근거는 `inventory/performance-implementation-2026-10-13.json`에서 관리한다.

## 적용한 변경

| 대상 | 변경 | 보존한 동작 |
|---|---|---|
| WebStreamer | 원본 HTTP 바이트 64 MiB LRU 캐시, 같은 URL 요청 합치기, 이미지 HTTP 4개·디코더 2개 분리, 취소와 네이티브 버퍼 해제 개선 | PNG/SVG 디코딩·해상도·안티앨리어싱, 기존 HLS 경로 |
| MTR–BlueMap | 숫자 노선 ID 인덱스, Core가 정렬한 결과의 재정렬·복사 제거, 역별 primitive 카운터 | 공개 노선 정책, 동률 순서, 만료·취소, 플랫폼별 128개·역별 8개 제한, 2초 갱신 |
| MSD | 기존 ID와 유지 ID를 요청/응답 처리마다 해시 집합으로 구성 | 직렬화 순서와 중복 ID 의미, 변경 시 그래프 재구축 |
| Minefed client compat | 입력 픽셀·설정·프레임 치수에 따른 32 MiB 변환 결과 캐시, PFM 파일 지문 스트리밍 계산 | 기존 픽셀 변환과 리소스 변경 감지, 기존 PFM 캐시 이관 |
| BlueMap | 재사용하는 4바이트 버퍼로 PRBM 숫자 필드 출력 호출 합치기 | raw/gzip 바이트, 쓰기 시점, 예외와 close 계약 |
| Chisels & Bits | 한 client tick에서 우선순위 점수를 재사용하고 선형 heapify로 순위 구성 | FIFO 동률 처리, 새 요청·승격·rerun 갱신, 기존 동적 scorer API |

WebStreamer는 서버의 `max-age`, `Age`, `Expires`, ETag/Last-Modified, `no-store`와 `no-cache`를 따른다. 캐시가 유효하고 퇴출되지 않은 재방문은 HTTP 요청이 필요 없다. 만료된 원본은 조건부 요청으로 갱신한다. 첫 실패의 재시도 대기는 30초에서 1초로 줄고 반복 실패하면 최대 30초까지 늘어난다. 응답 헤더는 5초, 본문은 데이터 수신이 **중단된 시간만 30초** 제한한다. 정상적으로 계속 전송되는 큰 이미지를 총 전송 시간 때문에 중단하지 않는다. 64 MiB는 보관 캐시의 한도이며, 진행 중 요청·디코드·GPU 메모리를 모두 합친 한도는 아니다.

클라이언트의 중복 Minefed 리소스팩 제거는 앞선 변경을 유지한다. Minefed 팩은 서버에서 제공하며, Yuushya Foliage Addon과 모드 내장 자산은 유지한다.

## 수치로 확인한 범위

| 검사 | 결과 | 해석 범위 |
|---|---|---|
| Atlas 변환, 실제 텍스처 8,928개 | 출력 동일. 반복 변환 5회 중앙값 828.631 → 420.067 ms | 약 49.3% 단축은 픽셀 변환 단계만 해당. PNG 해독·모델 베이크·GPU 업로드 제외 |
| PFM 1,911개 파일 지문 | 1,684,688 → 156,702자, 약 90.7% 감소 | 파일 전체 byte[]와 hex 문자열 보관 제거. 기존 디스크 캐시는 다음 정상 저장 전까지 큰 형식을 유지 |
| PFM 탐색·JSON 계산 | 1,738.736 → 1,747.791 ms | 이 검사에서는 시간 개선 확인 안 됨. 디스크 저장 시간 제외 |
| BlueMap 8,193 triangle PRBM | 출력 774,320바이트 동일. backend 호출 774,286 → 359,509회 | 약 53.6% 감소는 Java 출력 메서드 호출 수. 디스크 syscall 수가 아님 |
| BlueMap 동일 입력 커널 | 41회 교대 중앙값 26.6342 → 15.5140 ms | 약 41.8% 단축. 메모리 출력이며 압축·디스크·월드 렌더링 제외 |
| C&B 2,048건 처리 점수 계산 | 기존 2,098,176회. epoch당 1/4/8건 처리 시 2,098,176 / 525,312 / 263,168회 | 약 0 / 75.0 / 87.5% 감소. 실제 FPS·tick 시간 측정값이 아님 |

Atlas 캐시 최초 채움에는 픽셀 지문 스캔 비용이 추가된다. 이 때문에 반복 변환 개선율을 최초 시작 시간에 적용하지 않는다. C&B도 epoch에서 한 건만 처리하면 점수 계산 수가 줄지 않고 순위 구조 비용이 추가될 수 있다.

제공된 서버 JFR에서 이번 MTR 후처리의 관련 표본은 Server thread Java 표본 **35/295**였다. 해당 부분이 2~3배 빨라진다고 가정하면 Java 표본 작업량의 약 **5.9~7.9%** 감소에 해당하지만, 이는 조건부 계산이다. 실제 MSPT·TPS·서버 CPU 개선을 측정한 값이 아니다. 차량 상세 생성 등 Core 내부 도착 정보 계산은 이번 변경에 포함하지 않았으므로 전체 도착 정보 83개 표본을 모두 최적화 대상으로 간주하지 않는다.

## 기능 검증

- WebStreamer: 전체 33개 테스트 통과. GET/304·캐시 지시자·동일 URL 합치기·본문 수신 정지·제한 시간을 축소한 테스트에서의 지속 전송·취소·완료 경쟁·기존 렌더 거리/HLS 검사 포함. Java 클래스 major 61, 내장 JAR 15개와 라이선스 바이트 동일.
- MTR: JUnit 123개와 지도 웹 테스트 23개, rail rendering·Mixin·LightType 검사 통과. 실제 이전/신규 도착 응답의 JSON 동등성도 확인.
- MSD: 이전 구현과 160개 동등성 비교 및 기존 26개 응답 계약 통과. 937개 렌더 스케줄 비교·24개 light query 비교·6,757개 assertion, 4,812개 sign 계약 검사 및 remapJar 성공.
- Compat: Atlas·PFM 캐시·PTS·PFM·TrafficCraft 검증과 빌드 통과. 같은 크기·수정 시각의 내용 변경, 삭제, 버전·loader·variant 변경도 캐시를 무효화함을 확인.
- BlueMap: raw/gzip 18개 출력 동등성 비교. Core 검사 41개 중 실패/오류 0, 기존 선택적 export fixture 1개 skip. 신규 PRBM 테스트 6개 포함.
- Chisels & Bits: 전체 Core 테스트 56개와 Fabric 빌드 통과. epoch 재사용·동적 API 혼용·우선순위 승격/하향·동점 순서·rerun·scorer 실패를 검사.
- 상위 저장소: 빌드·모드 관리·리소스팩 패키징 테스트 129개 중 실패 0, 선택적 검사 1개 skip.
- 통합 클라이언트: 시작·팩 적용·해제 모두 완료하고 각 단계의 129개 showblock 모델 검사 통과. 기존 86개 리소스 진단의 종류와 대상은 변경 전후 동일하며, 이 기존 경고까지 해결했다는 의미는 아님.
- 서버 측: 최종 JAR가 포함된 Fabric Loader의 `MixinEnvironment.audit()` 통과. preLaunch 검사이며 운영 월드 tick 성능 검사가 아님.
- 6개 최종 JAR의 SHA-256과 ZIP CRC 재검증 통과. Java 21은 일부 Gradle 실행에 사용하며 게임 실행 요구 조건은 Java 17로 유지.

## 실제 클라이언트 비교

| 단계 | 변경 전 | 변경 후 | 이번 관측 차이 |
|---|---:|---:|---:|
| 시작 및 제목 화면 표시 | 133.501초 | 131.830초 | 1.3% 감소 |
| 리소스팩 적용 | 60.614초 | 56.743초 | 6.4% 감소 |
| 리소스팩 해제 | 66.754초 | 53.196초 | 20.3% 감소 |

각 조건을 한 번 실행한 참고값으로 통계적으로 확정된 개선율이나 다른 PC의 예상치는 아니다. 같은 72개 JAR의 모드팩 사본에서 후보의 6개 모드 ID만 교체하고 동일한 Java 17, `-Xms1G -Xmx8G`, JFR profile 설정을 사용했다. 이 작업의 Gradle 빌드와 게임 실행은 공용 잠금으로 직렬화했다. 실행 순서·OS 파일 캐시·다른 호스트 작업의 영향은 남는다. 시작 시간의 확실한 개선은 이 한 번의 비교만으로 주장하지 않는다.

교체용 로컬 묶음은 `build/performance-20261013/minefed-performance-patch-20261013.zip`이다. 6개 JAR, 해시와 원격 소스 커밋, 교체 안내를 포함한다. 현재 설치된 클라이언트의 JAR 및 운영 서버는 교체하지 않았다.

## 남아 있는 병목과 적용 범위

변경 전 단독 클라이언트 실행은 시작 **133.501초**, 팩 적용 **60.614초**, 해제 **66.754초**였다. 게임 전체 리소스 관리자에서 서버팩과 같은 내용의 로컬 ZIP을 켜고 끄는 검사이며 서버 다운로드·인증·팩 응답 프로토콜은 측정하지 않는다. 빌드와 겹친 첫 실행은 메모리 경합으로 시작 345.497초가 걸려 성능 비교에서 제외했다.

변경 전 baseline-b1의 유효한 클라이언트 JFR에서 모델 로딩·베이크를 포함한 Java 실행 표본은 팩 적용 **2,899/3,379(85.8%)**, 해제 **3,528/3,922(90.0%)**였다. GC 정지 합계는 각각 2.219초와 2.563초였다. 전체 모델 로딩·베이크 비용이 여전히 크며, 캐시 키의 병적인 재귀나 해시 충돌이 주원인이라고 단정할 근거는 없었다. 이 표본 비율은 벽시간 비율이나 예상 절감률이 아니다. 모델·텍스처를 삭제하거나 FerriteCore 중복 제거를 비활성화하는 방법은 사용하지 않았다.

C&B 큐 초과 시 모델 갱신이 누락될 가능성은 우선순위 개선만으로 해결되지 않는다. 현재 scheduler는 좌표만으로 완료 항목을 찾고 worker 교체·월드 전환·실패 시 callback 수명도 함께 관리해야 한다. 안전한 재요청에는 entry identity와 실패 완료, 월드 정리까지 별도 검증이 필요하므로 단순히 큐를 무한히 늘리거나 재시도를 추가하지 않았다.

서버의 `ticks behind` 경고 발생 시각과 제공된 JFR 수집 시각이 달랐다. 이번 구현이 해당 경고를 제거했는지는 운영 환경에서 적용 후 같은 부하의 JFR/MSPT와 경고 횟수를 다시 확인해야 한다. 서버 파일은 이번 작업에서 변경하지 않았다.
