# 사용자 장비 클라이언트 성능 측정 — 2026-10-06

사용 중인 장비에서 기존 모드팩의 전경 플레이 기준을 수집하고, 관측된 MTR의
반복 객체 생성과 리소스 캐시 순회 비용을 줄였다. 재시작 후 같은 이동 경로를 거친
기존 JAR 대조군 **A2는 34.9895 FPS**, 수정군 **B2는 36.2244 FPS**였다.
합산 FPS는 3.53% 높았고, 렌더 루프 시간 p95는 **45.7206→38.2827ms**,
p99는 **56.9201→47.1715ms**로 낮았다. 각각 약 10초씩 세 번 측정한 한 장면의
관측값이며 서버 상태와 JVM 이력이 완전히 같지 않아 일반적인 개선율로 확정하지 않는다.

최초 thunder 조건의 33.9919 FPS와 조건이 다른 중간 기록은 별도로 보존한다.
중간 수정군의 58.2789 FPS와 29.7395 FPS는 작업량·JIT 상태가 달라 개선율로 쓰지
않는다. 같은 수정 JVM에서 **VSync만 끄고 최대 60 FPS를 유지한 추가 시험은
55.9664 FPS**였다. 화질·거리 감소 없이 이 장비의 로컬 프로필에 해당 설정을
유지했다. 커서 수정의 설치·코드 검사는 완료했으며, 네이티브 CEF를 포함한 커서
이탈 재현 시험은 수행하지 않았다.

`client/metrics/ticking.csv`의 `ticktime`은 나노초 단위여서 1,000,000으로 나눠
밀리초로 변환했다. Minecraft 1.20.4의 recorder는 `render(boolean)` 호출 전후를
감싸므로 이 값은 **클라이언트 렌더 루프 시간**이다. 서버 TPS나 20Hz 클라이언트
게임 틱 시간이 아니다. 최초 기준의 각 ZIP에서 렌더 호출 수·CSV 행 수·프로파일
Tick span이 일치했으며 별도의 `#clientTick` 개수는 204 / 202 / 202였다.

FPS는 전체 렌더 루프 수 / 프로파일 경과 시간으로 계산했다. 백분위는 정렬한
표본의 `ceil(p × n)`번째 값인 nearest-rank를 사용한다. `updateDisplay`에는 버퍼
교환뿐 아니라 FPS 제한 대기도 포함된다. 이 측정은 GPU의 실제 화면 표시 간격을
직접 측정한 결과가 아니다.

F3+L ZIP 이름은 KST 초 단위의 보고서 내보내기 시각이며, 내부 프로파일에는 절대
시작·종료 시각이 없다. OS 통계 정렬에는 ZIP 이름 시각에서 기록 길이를 뺀 추정
구간을 사용했다. ZIP 파일 완료 시각도 별도로 보존했으며, 프레임 기록의 절대
시각이 밀리초까지 정확하다고 주장하지 않는다.

## 이번 수정과 함께 설치한 기존 수정

1. **같은 월드의 가림 판정용 BlockView를 재사용한다.**
   `d0be6a9295c0739cd186484699193c243d4f48b5`는 `prepareChunk`가 같은 월드를
   반복 준비할 때 매번 만들던 불변 래퍼를 재사용한다. 블록 상태·가림 결과를
   캐시하지 않으며 월드 변경·null 월드·cleanup 때 참조를 갱신하거나 비운다.
   실제 라이브러리는 미확인 voxel마다 이 준비 경로를 호출하므로 반복 할당을
   줄이는 대상이다. 독립 합성 검사에서 prepare당 할당은 32.000→16.250바이트였다.
   이 값은 게임 FPS 개선율이 아니다.
2. **리소스 만료가 아직 없으면 전체 캐시 순회를 건너뛴다.**
   `8167073c541f88996eb2ab4a184f1c27aac2462b`는 다음 만료 시각과 데이터 갱신
   revision, 수집된 weak reference를 확인해 필요한 tick에만 순회한다.
   매 tick의 로딩 예산 복원, 만료 경계의 `currentMillis > expiry`, supplier 호출,
   강제 로드, 시계 역행과 수집 처리를 보존한다. 죽은 참조는 한 번의 압축으로 제거한다.
3. **10월 5일 캐시·커서 수정도 이번 설치에 포함했다.**
   MTR `13e1789dde2be749d0ece45c2847b14913e4fb93`의 거리 16 이하 연속 배열 /
   더 먼 거리 희소 캐시 선택과 display 1.0.1의 월드 디스플레이 커서 이벤트 차단을
   함께 적용한다. 두 수정은 측정 시작 때 설치되어 있지 않았으므로 전후 결과를
   이번 두 MTR 변경만의 효과로 분리할 수 없다.

| 단계 | 조건 / ZIP 시각(KST) | 합산 FPS | p95 / p99(ms) | 해석 |
| --- | --- | ---: | ---: | --- |
| 최초 기준 | 기존 JAR, thunder / 03:51:37, 03:52:03, 03:52:32 | 33.9919 | 43.4169 / 73.5173 | 초기 진단 자료, 최종 주 대조군과 구분 |
| `patched-early` | 수정 JAR, 경로 재설정 전 / 04:08:42, 04:09:04, 04:09:30 | 58.2789 | 19.5668 / 26.4099 | 가림 판정 작업량이 작아 성능 개선 비교에서 제외 |
| `patched` | 같은 수정 JVM에서 경로 재설정 후, clear / 04:14:43, 04:15:06, 04:15:42 | 29.7395 | 49.4873 / 69.3469 | 대량 deoptimization과 다른 워밍업 이력; 진단 기록 |
| **A2** | 기존 JAR로 새 JVM, 즉시 동일 경로, clear / 04:24:36, 04:25:05, 04:25:29 | **34.9895** | **45.7206 / 56.9201** | 최종 비교의 주 대조군 |
| **B2** | 수정 JAR로 새 JVM, 즉시 동일 경로, clear / 04:32:43, 04:33:11, 04:33:42 | **36.2244** | **38.2827 / 47.1715** | 같은 설정의 최종 수정군 |

`patched-early`의 MTR 가림 판정 작업 스레드 Java 표본은 30초 JFR에서 3개였고,
경로 재설정 후 `patched`에서는 2,246개, A2에서는 2,231개였다. 따라서 초기에
관측한 약 58 FPS를 기존 약 34 FPS에 대한 개선으로 보고하지 않는다. 샘플 개수는
정확한 호출 수나 CPU 시간이 아니지만, 초기 기록의 작업량 불일치를 보여 준다.

`patched`의 30초 JFR에는 `jdk.Deoptimization`이 **464,185회** 기록됐고,
그중 **463,447회**가 `VertexAttributeState.apply`의 `unstable_if / action=none`이었다.
이 기록은 FPS 기록과 별도의 시간대이므로 각 느린 프레임의 원인으로 직접 연결하지
않는다. 같은 JVM의 초기 장면·경로와 JIT 워밍업 상태가 달랐다는 교란 요인으로 남기고,
새 JVM의 B2로 재확인했다.

기존·수정 JAR의 `VertexAttributeState`, 내부 클래스, `VertexAttributeType`,
`VertexAttributeStateMixin`, `OptimizedRendererBuffers`는 **클래스 바이트가 동일**했다.
mapping 항목의 변경도 없었다. 따라서 이 관측만으로 새 수정이 해당 메서드의 코드를
악화시켰다고 판단할 수 없다. 반대로 바이트 일치가 다른 변경의 간접 영향까지
배제하는 것은 아니다. 새 JVM에서 다시 측정한 A2/B2를 주 비교로 사용한다.

`patched`의 OS 기록은 04:14:24.437~04:16:24.408 KST로 세 FPS 기록은 포함하지만,
JFR 04:16:09~04:16:39 KST의 **앞쪽 약 15.4초만 포함**한다. 나머지 약 14.6초의
전경 여부는 이 OS 수집으로 확인하지 못했다. 따라서 수정군의 모든 JFR 구간이
전경이었다고 기록하지 않는다. A2의 세 FPS 기록과 JFR은 181/181 전경 표본 구간에
모두 포함된다.

A2는 1,050프레임 / 30.009초였고, B2는 1,088프레임 / 30.035초였다.
날씨와 경로는 맞췄지만 시각·엔티티 상태와 JVM 워밍업의 차이는 남는다.

OS CPU는 프레임 기록의 추정 구간에 맞춘 가중 평균이며 JFR 수집 중 통계와 섞지 않았다.

Java 표본은 측정된 스택 수다. 같은 스택에서 여러 메서드가 집계될 수 있으므로
행을 합산하거나 정확한 실행 시간·호출 수로 해석하지 않는다.

이는 새 JVM의 통일된 진입 경로에서 얻은 관측이며, 중간 기록의 원인을 확정한 것은 아니다.

## 추가 설정 시험과 최종 로컬 옵션

B2와 같은 JVM·위치·시선에서 게임 UI로 VSync만 끄고 최대 60 FPS를 유지했다.
각 ZIP의 옵션과 장비 정보를 비교했으며 화질·거리·854×480 프레임버퍼는 같았다.
이 결과는 위의 동일 설정 A2/B2 코드 비교와 구분한다.

| 지표 | B2 VSync 켜짐 | 같은 B2 JVM에서 VSync 끔 |
| --- | ---: | ---: |
| 합산 FPS | 36.2244 | 55.9664 |
| 렌더 루프 p50(ms) | 26.2292 | 16.6649 |
| 렌더 루프 p95(ms) | 38.2827 | 22.1049 |
| 렌더 루프 p99(ms) | 47.1715 | 41.3187 |
| 최장 렌더 루프(ms) | 92.7267 | 71.4452 |
| 50ms / 100ms 초과 프레임 | 4 / 0 | 11 / 0 |
| FPS 구간 프로세스 CPU | 12.87% | 19.72% |
| FPS 구간 시스템 CPU | 21.95% | 33.42% |

VSync 끄기 기록은 04:42:51 / 04:43:32 / 04:43:56 KST ZIP이며,
각 54.5836 / 55.0175 / 58.3000 FPS, 합산 1,680프레임 / 30.018초였다.
이 장면에서 합산 FPS는 54.50% 높았다. p95/p99가 낮아졌지만 50ms 초과 프레임 수와
CPU 사용량은 늘어 모든 지연·자원 지표가 개선된 것은 아니다. 더 오래 실행된 같은
JVM에서 순서대로 한 시험이며, 반복 교차 실험으로 일반화한 수치가 아니다.

FPS의 OS 수집은 04:42:27.844~04:44:27.800 KST의 **121/121 전경 표본**으로
세 기록을 모두 포함했다. 별도 JFR은 04:44:38.107~04:45:08.107 KST이고,
전용 OS 수집 04:44:23.821~04:45:23.803 KST의 **61/61 전경 표본**에 모두 포함됐다.
두 OS 수집을 구분해 정렬했으며 첫 수집이 나중 JFR까지 포함한다고 가정하지 않았다.

VSync를 끈 JFR에도 MTR 작업 스레드 Java 표본 2,262개와 차량 779 / 선로 1,037 /
MSD 411개의 가림 판정 포함 표본이 있었다. 렌더 스레드 Java 표본은 687개,
`MainRenderer` 615개, draw 경로 485개였다. 실제 선로·차량 렌더 및 가림 판정 부하는
유지됐으며 초기 `patched-early`처럼 작업량이 거의 없는 결과가 아니었다.
렌더 / 작업 스레드 할당은 150.70 / 45.01 MiB/s로, 더 많은 프레임과 함께 렌더
할당률도 증가했다. deoptimization 6건은 JFR 자체 스레드였고
`VertexAttributeState`의 대량 발생은 없었다.

이 장비의 최종 로컬 옵션은 **VSync 끔 / 최대 60 FPS**로 유지했다. VSync를 끄면
화면 찢어짐이 보일 수 있다는 절충이 있다. 해당 현상이 거슬리면 게임 설정에서
VSync를 다시 켤 수 있다. 화질·렌더 거리 감소나 모드 전체 기본값 변경은 적용하지 않았다.

## 커서 수정의 확인 범위

display 1.0.1의 설치 해시와 소스 회귀 검사를 확인했다. 월드 디스플레이용 브라우저의
커서 이벤트 차단 경로를 검증했으며 해당 수정이 포함된 산출물을 설치했다.
다만 실제 네이티브 CEF 페이지의 초기 생성·재표시 중 커서 잠금 유지와 메뉴·Alt+Tab의
정상 해제를 함께 재현하는 시험은 **수행하지 않았다**. 따라서 커서 이탈 증상이
사용자 환경에서 해소됐다고 확정하지 않는다.

## 로컬 진단 자료

원시 JFR, F3+L ZIP, OS 표본, 환경·분석 JSON, 백업과 설치 영수증은 Git에서 제외한
`.cache/performance/20261006-live/`에 보존한다. 최초 기준값은
`baseline/summary.json`, `baseline-validation.json`, `baseline-repeat-os/os.csv`,
`baseline-repeat-analysis.json`에서 가져왔다. 초기 전경 확인 범위가 일부 빠진
`baseline-preliminary` 기록은 최초 기준값에 섞지 않았다. 이후 단계는
`patched-early/summary.json`, `patched/summary.json`, `a2/summary.json`,
`b2/summary.json`, `a2-validation.json`, `b2-validation.json`과 각 단계의
OS·환경·JFR 분석 JSON으로 구분한다. deoptimization은 `patched-deopt.json`,
클래스 바이트 비교는 `vertex-bytecode-comparison.json`에 기록했다.
추가 설정 시험은 `vsync-off/summary.json`, `vsync-off-validation.json`과 별도의
`vsync-off-os`, `vsync-off-jfr-os`, `vsync-off-analysis.json`으로 구분한다.

JFR 내부 임시 저장소와 출력 모두 실제 ASCII 경로를 사용한 뒤 로컬 작업 폴더로
보존했다. 원시 기록에는 환경·프로세스 정보가 포함될 수 있어 공개 Git이나 외부
서비스에 업로드하지 않는다. 운영 서버 TPS/MSPT는 이번 클라이언트 측정에 포함되지 않는다.
