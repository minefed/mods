# 실행 중인 Minefed 클라이언트 성능 분석 — 2026-09-21

실행 중이던 Minecraft에서 직접 짧은 이동과 시야 변경, 설정별 비교 측정을 했다.
**관측한 철도 지역의 주된 병목은 MTR 기본 3D 선로 렌더링이며, 수직동기화가 표시 대기를 늘려 저FPS를 악화시킨다.**
수직동기화와 기본 3D 선로를 모두 끄면 같은 지역에서 평균 **63.6 FPS**가 나왔고,
3D 선로만 다시 켜면 **24.0 FPS**로 내려갔다. 기본 설정에서는 **16.4~18.5 FPS**였다.
이 결과는 이 장소·해상도·장비에서의 측정이며 모드팩 전체 장소의 성능을 보장하지 않는다.

측정은 2026-09-21 00:29~00:51 KST에 수행했다. 분석 후 시험용 설정은 모두 원래 값으로 복원했다.
게임 재시작, 모드 JAR 교체, 운영 서버 파일 변경·업로드·재시작은 수행하지 않았다.

F3+L의 `client/profiling.txt`에 나오는 `Tick span`은 여기서는 클라이언트 렌더 루프 횟수다.
같은 파일의 `gameRenderer` 호출 횟수와 일치하며, 별도의 `#clientTick` 횟수와 다르다.
아래 FPS는 **렌더 루프 횟수 / 기록 시간**으로 계산했다. 이를 서버 TPS로 해석하면 안 된다.
프레임 시간은 `client/metrics/ticking.csv`의 나노초 값을 밀리초로 변환했다.
95백분위는 정렬한 관측값에서 가장 가까운 순위로 계산했다.

F3와 프로파일러 자체의 비용, 실시간으로 움직이는 차량, 다른 프로세스의 부하가 포함된 실환경 측정이다.
최초 수평 시야와 후속 아래 방향 시야는 구분했다. 설정 비교 중에는 렌더 거리·해상도·리소스팩을 바꾸지 않았다.

3D를 끈 10초 기록에는 50ms를 넘는 프레임이 없었다. 초기 10초 기록에서는
185개 중 53개가 50ms, 22개가 100ms를 넘었다. 평균 FPS 외에 긴 프레임 지연도 크게 줄었다.
3D를 복원했을 때 다시 느려지는 결과까지 확인해 단순한 실행 시간 경과나 일회성 변동과 구분했다.
첫 VSync 해제 기록은 JFR 시작과 일부 겹치므로, 반복 기록과 복원 기록도 함께 제시한다.

**원인에 대한 근거**

1. **MTR 선로와 차량 렌더링이 Java 측 부하를 지배한다.**
   60초 JFR의 렌더 스레드 Java 실행 샘플 933개 중 691개(74.1%)가
   `org.mtr.mod.render.MainRenderer.render`를 통과했다.
   325개(34.8%)에는 `RenderRails.lambda$renderRailStandard$13`이 있었고,
   `StoredMatrixTransformations.transform`, `Matrix4f.rotate`, `Matrix3f.rotate`가 반복됐다.
   이는 서로 겹치는 스택 비율이며 합산하거나 CPU 시간 비율로 그대로 간주하지 않는다.
   3D 옵션을 실제로 껐다 켠 비교 결과도 이 실행 경로의 부담을 뒷받침한다.

2. **가림 판정도 MTR의 추가 CPU 비용이다.**
   전체 Java 실행 샘플 3,540개 중 2,596개는 MTR `WorkerThread`에 속하는 `Thread-208`에서 나왔다.
   `OcclusionCullingInstance.isAABBVisible`, 캐시 조회, 블록 상태 조회와 `Arrays.fill`이 주요 경로였다.
   가림 판정 작업이 렌더 스레드와 별도로 수행된다는 뜻이며, 렌더 스레드가 그 시간 전체를 기다렸다는 뜻은 아니다.

3. **VSync/화면 표시 대기가 저FPS를 증폭한다.**
   초기 프로파일에서 `updateDisplay`가 전체 프레임 시간의 57.27%,
   같은 아래 방향 기준 측정에서는 52.60%였다.
   JFR에서도 `glfwSwapBuffers` 대기가 관측됐다.
   VSync 해제 후 `updateDisplay` 비중은 9.60~19.39%로 줄고 FPS가 개선됐다.
   이는 이 환경에서 표시 동기화의 영향이 크다는 근거이며, 특정 GPU 드라이버 결함을 확정하는 증거는 아니다.

4. **힙 부족이나 긴 GC 정지가 지속적인 저FPS의 주원인은 아니다.**
   초기 90개 jstat 표본에서 Full GC는 0회였고 누적 GC 시간 증가량은 약 47ms였다.
   60초 JFR의 GC 정지 7회 합계는 62.7ms, 최장은 26.7ms였다.
   GC 후 힙 사용량은 대체로 약 3.3 GiB였다.
   JFR `GarbageCollection.duration`에는 동시 작업 시간이 포함될 수 있어 정지 시간으로 쓰지 않았다.
   다만 렌더 스레드는 할당 카운터 차이로 약 237 MiB/s의 임시 객체를 만들고 있었다.
   MTR 객체 생성·변환 비용은 개선 대상이지만, 현재 증거로 JVM 메모리 누수라고 판정하지 않는다.
   할당 샘플의 가중치 합은 기록 시작 전 누적분 등으로 왜곡될 수 있어 이 속도 계산에는 사용하지 않았다.

5. **GPU 전체 포화·OS 메모리 고갈의 증거는 약하다.**
   초기 30초 OS 표본에서 전체 CPU 평균은 24.8%, 게임 GPU 3D 엔진 평균은 22.7%였고
   가용 메모리는 4,979~5,048 MiB였다.
   VSync 해제 후 게임 GPU 3D 평균은 33.9%, 3D 선로까지 해제한 표본에서는 21.5%였다.
   F3의 GPU 추정값과 Windows GPU 엔진 사용률은 계산 방식이 달라 서로 대체하지 않는다.
   전체 CPU가 낮다는 사실도 특정 스레드의 계산 비용을 부정하지 않는다.

6. **이번 관측에서 네트워크 왕복 지연은 낮았다.**
   F3 네트워크 그래프에서 최소 6ms, 평균 약 8ms가 관측됐다.
   표본 구간에 따라 최댓값은 12~56ms였고, 3D 복원 직후 약 70ms의 순간값도 보였다.
   지속적인 수백 ms 핑이 현재 저FPS를 설명한다는 근거는 없었다.
   렌더 루프가 늦어지면 입력·패킷 처리도 늦게 보일 수 있다.
   **운영 서버 TPS/MSPT는 측정하지 않았으므로 서버 틱 지연을 완전히 배제하지 않는다.**
   클라이언트 JFR의 `minecraft.ServerTickTime`은 0 값의 주기 이벤트였고 서버 성능 자료로 사용하지 않았다.

로그의 `CapturingVertexConsumer` 최적화 경로 미지원 경고는 MTR/Sodium 연동의 추가 조사 단서다.
이번 비교만으로 Sodium 충돌이나 이 경고 자체가 원인이라고 확정하지 않는다.
초기 리소스 로딩 경고와 중복 ID 경고도 현재 프레임 비용과 구분한다.

**개선 우선순위**

- 즉시 적용할 후보는 MTR 대시보드 → 설정 → `Render default rails in 3D: Off`,
  비디오 설정 → `수직 동기화: 끔`이다. 이 두 변경은 실행 중 비교로 효과를 확인했다.
  전자는 기본 선로 모양을 단순화하고, 후자는 화면 찢어짐이 생길 수 있다.
  적용 후에는 실제 이동 경로와 평소 창 크기에서도 프레임 시간을 재확인한다.
- 코드 개선은 `RenderRails.java:252` 이후의 반복 구간별 위치·조명 조회와 행렬/콜백 생성을 줄이는 작업,
  `StoredMatrixTransformations`의 반복 변환 계산 캐시, MTR 렌더 배치 처리,
  `WorkerThread.java:33` 이후 가림 판정의 반복 계산·캐시 초기화 비용을 우선 조사한다.
  렌더 거리 축소도 후보지만 이번에는 개별 효과를 측정하지 않았다.
- Java 힙을 무작정 늘리거나 모드 전체를 업데이트하는 조치는 이 측정의 첫 해결책으로 뒷받침되지 않는다.
  위 렌더링 부담을 줄인 뒤에도 블록 반응·이동 판정 지연이 남으면 별도로 서버 TPS/MSPT와 프록시 경로를 측정한다.

**버전과 보존한 자료**

설치된 MTR JAR는 Minecraft 1.20.4/Fabric용 `fabric-4.0.5.jar`이며 SHA-256은
`6eba7fb9602c1428e4d0861ae8810c5b7e7183ba28bb5c46b71b97780fe713ad`다.
설치 manifest와 해시가 일치한다. manifest의 소스 추적 브랜치는
`codex/fix-mixin-loader-compatibility`, 전체 커밋은
`139b0170d9065673767d7caa988847505c310ca0`이며 로컬 소스도 이 커밋이었다.
기존 초기 설치 manifest 버전과 이후 추가 수리 이력이 있으므로 초기 manifest 이름만으로 전체 현재 구성을 판단하지 않았다.

집계 JSON/CSV, 각 조건의 게임 프로파일과 메트릭, JFR 3개와 분석 결과, OS 표본,
설정 백업, FPS·핑 스크린샷은 로컬 `.cache/performance/20260921-live/`에 보존했다.
원시 진단 자료는 Git에 추가하거나 외부 서비스에 업로드하지 않았다.
JFR 파일에는 환경·프로세스 정보가 포함될 수 있으므로 보고서와 분리해 보관한다.
초기 한글 경로 대상 JFR 기록은 0바이트여서 분석에서 제외했고 유효한 기록을 다시 수집했다.

최종적으로 `options.txt`, `sodium-options.json`, `mtr.json`을 측정 전 백업과 행 단위로 비교해
설정 차이가 없음을 확인했다. 측정용 대시보드 아이템도 단축바에서 정리했다.
